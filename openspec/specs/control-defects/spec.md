# control-defects Specification

## Purpose
Каталог контрольных дефектов — заведомых ошибок, которые ОТК обязан найти: безопасное применение к копии,
таблицы паритета с Конфигуратором и сравнения с анализаторами BSL из прогона.

## Requirements

### Requirement: Каталог контрольных дефектов

ОТК SHALL содержать каталог контрольных дефектов: патч к исходникам, ожидаемый шаг, который
его ловит, и ожидаемый исход. Минимальный набор:

| Дефект | Ожидаемый шаг |
| --- | --- |
| синтаксическая ошибка в невызываемой функции | compile-probes |
| необъявленная переменная | compile-probes, static-checks (BSL LS) |
| вызов несуществующей процедуры модуля | compile-probes |
| `Справочники.<опечатка>` в неисполняемой ветке (рядом верные `Константы.<имя>` и `ПланыОбмена.<имя>`:
заимствование константы и плана обмена во временное расширение extcheck) | static-checks, extcheck |
| несуществующий предопределённый элемент | static-checks |
| опечатка в поле запроса | query-check |
| удалённый экспортный метод с вызывающими | change-detection (зависимые) + static-checks |
| лишний параметр в вызове экспортного метода | static-checks |
| переименован обработчик события формы | static-checks |
| несуществующая форма в `ОткрытьФорму("...")` | static-checks |
| `Вопрос()` в модуле объекта вне `#Если` | compile-probes (ExternalConnection) или `uncovered` |
| ошибка в клиентской процедуре модуля формы | compile-probes (ThinClient) |
| ошибка в модуле сеанса | compile-probes (старт сеанса) |
| метод, недоступный только в веб-клиенте (`КомандаСистемы`) | extcheck (-WebClient) |
| вызов несуществующей процедуры в модуле управляемой формы (выгрузка Конфигуратора) | extcheck |
| метод, недоступный только в веб-клиенте, в модуле формы (выгрузка Конфигуратора) | extcheck (-WebClient) |
| вызов несуществующей процедуры в модуле объекта (выгрузка Конфигуратора) | extcheck |
| исключение в обработчике открытия формы (`ПриОткрытии`) | form-smoke |
| зависание формы при открытии (бесконечный цикл в `ПриОткрытии`) | form-smoke |
| метод глобального контекста более новой линейки, чем режим совместимости (по справке платформы) | static-checks, compile-probes, extcheck |
| метод той же линейки новее режима совместимости | static-checks (предупреждение) |
| конструктор новее режима совместимости | static-checks (предупреждение) |

Дефект, который Конфигуратор пропускает, а ОТК отмечает предупреждением (код новее режима совместимости), SHALL
считаться пойманным находкой уровня «предупреждение».

Дефект, для которого в проекте нет цели (нет клиентского общего модуля, форм, модуля сеанса…), SHALL
отмечаться в отчёте строкой «контроль не построен» с причиной, а не пропадать из таблицы молча.

#### Scenario: Дефект пойман

- **WHEN** `otk controls` применяет дефект и запускает `gate`
- **THEN** код выхода 1, а падение пришло от ожидаемого шага

#### Scenario: Дефект пропущен

- **WHEN** ОТК не поймал дефект
- **THEN** `controls` завершается с кодом 1 и называет дефект и шаг, который должен был его поймать

### Requirement: Безопасное применение

Контрольные дефекты SHALL вноситься в отдельный коммит, собранный в git-объектах (временный индекс,
`commit-tree`) и не попадающий ни на одну ветку; рабочее дерево, индекс и ветки разработчика, origin и
исходники только для чтения SHALL оставаться неизменными.

#### Scenario: Прерванный прогон

- **WHEN** `controls` прерван посреди прогона
- **THEN** рабочее дерево, индекс и ветки разработчика не изменены; копия ИБ при следующем `gate` пересобирается по разнице с коммитом дефектов

### Requirement: Дефект, ломающий старт сеанса

Если сеанс (COM или YAxUnit) не стартовал из-за модуля с дефектом, ОТК SHALL перепроверить
пропущенные дефекты отдельным прогоном без этого модуля, а не засчитывать их пропуск.

#### Scenario: Удалённый экспорт ломает модуль, используемый при старте

- **WHEN** после удаления экспортного метода не стартует сеанс, и опечатка в запросе другого модуля не проверена
- **THEN** опечатка проверяется повторным прогоном без удалённого метода и засчитывается по его результату

### Requirement: Таблица паритета с Конфигуратором

ОТК SHALL уметь прогонять тот же каталог через проверку всех модулей Конфигуратором и строить
таблицу «дефект → ловит Конфигуратор / ловит ОТК».

Для проекта-конфигурации эталонов SHALL быть два: проверка основной конфигурации и тот же код,
заимствованный во временное расширение так, как это делает extcheck (`/CheckModules … -Extension`); их
расхождение — отдельный раздел таблицы с причиной. `controls --parity --doc <файл>` SHALL писать документ
(`docs/vs-designer.md`): условия прогона (конфигурация, платформа, режим совместимости, режимы проверки,
коммит), таблицу и сноски к утверждениям, которые верны при условии.

Кроме синтаксического контроля (`/CheckModules`) эталоном SHALL быть и полная проверка конфигурации
`/CheckConfig` со всеми применимыми к конфигурации флагами: режимы модулей — как у `/CheckModules` плюс
клиент-серверные варианты; мобильные приложения и `-UnsupportedFunctional` — только при назначении
«Приложение для мобильной платформы»; поиск модальных и синхронных вызовов — только если конфигурация их не
использует. Вердикт полной проверки — по маркеру дефекта, как у синтаксического контроля: шумные проверки
(неиспользуемые процедуры, пустые обработчики) его не меняют. Документ SHALL содержать строку времени на пакет
дефектов: ОТК (`gate`), `/CheckModules`, `/CheckConfig`.

#### Scenario: Полная проверка ловит то, чего не ловит синтаксический контроль

- **WHEN** переименован обработчик события формы
- **THEN** столбец «Конфигуратор: полная проверка» — «да» (`-HandlersExistence`), «синтаксический контроль» — «нет»

#### Scenario: Эталоны расходятся

- **WHEN** Конфигуратор ловит дефект в основной конфигурации, а в расширении — нет (или наоборот)
- **THEN** документ называет дефект в разделе «Расхождение эталонов» с причиной или пометкой «не разобрана»

#### Scenario: Конфигуратор ловит, ОТК нет

- **WHEN** дефект ловит только Конфигуратор
- **THEN** таблица помечает его как пропуск, который надо закрыть или явно принять с обоснованием

### Requirement: Таблица «ОТК и анализаторы BSL»

`otk controls --analyzers` SHALL прогонять каталог контрольных дефектов через статику ОТК с обоими анализаторами
BSL (`environment.analyzer = "both"` на время прогона, без проб в базе — как `gate --static-only`) и строить
таблицу «дефект → ловит BSL LS / ловит bsl-analyzer / ловит остальная статика ОТК»: для анализатора — правила
и уровень (`fail`/`warn`) находок в файлах дефекта. В каталог на время прогона SHALL добавляться дефекты, на
которых проверяется семантика анализаторов и которых нет в обычном `controls`: функция без возврата на ветке,
метод, которого нет у типа значения, запрос к несуществующей таблице, серверный тип в клиентском модуле,
модальный вызов в клиентском модуле. Остальные дефекты каталога — те же, что в `controls`, со справочным
ожидаемым шагом. `--analyzers` несовместим с `--parity`.

`controls --analyzers --doc <файл>` SHALL писать документ (`docs/vs-analyzers.md`): условия прогона
(конфигурация, версии анализаторов, коммит), таблицу, расхождения анализаторов и вывод — анализаторы являются
источником находок внутри ОТК, а не альтернативой ему.

#### Scenario: Дефект ловит только один анализатор

- **WHEN** в функции общего модуля есть путь выполнения без `Возврат`, и находку дал только bsl-analyzer
- **THEN** в строке дефекта: bsl-analyzer — «да» с правилом и уровнем, BSL LS — «нет»; дефект назван в
  разделе «Расхождения анализаторов»

#### Scenario: Дефект ловит статика ОТК, а не анализатор

- **WHEN** в вызове экспортного метода другого модуля лишний параметр, и находку дала проверка
  `common-method`
- **THEN** столбец «статика ОТК» — `common-method`, столбцы анализаторов — по их находкам; обычный ожидаемый шаг
  дефекта показан справочно

#### Scenario: Анализатор не найден

- **WHEN** один из анализаторов не найден
- **THEN** его столбец — «не проверено» с причиной в условиях прогона; не найден ни один — команда завершается
  с ошибкой без таблицы
