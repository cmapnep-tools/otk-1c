# ci-integration Specification

## Purpose
Где запускается проверка: одна точка входа `otk gate` для хука pre-push, задания CI на PR и проверки всех
модулей Конфигуратором в CI; журнал срабатываний хуков.

## Requirements

### Requirement: Одна точка входа

ОТК SHALL запускаться одной командой `otk gate --base <ref>` одинаково локально, из
git-хука `pre-push` и в CI; различия задаются файлом настроек проекта и переменными окружения
(пути к платформе, базе, каталогу прогона).

#### Scenario: Локальный запуск

- **WHEN** разработчик выполняет `otk gate --base origin/master`
- **THEN** результат совпадает с тем, что даст CI на тех же ревизиях и той же платформе

### Requirement: Хук pre-push

ОТК SHALL предоставлять устанавливаемый хук `pre-push`, который запускает `gate` для
отправляемого диапазона и отменяет push при коде ≠ 0; обход — штатный `git push --no-verify`.

#### Scenario: Push с ошибкой

- **WHEN** в отправляемом коммите синтаксическая ошибка
- **THEN** push отменён, сводка выведена в терминал

### Requirement: Журнал срабатываний хуков

Хук pre-push и хуки Platform Tools (`otk pt`) SHALL дописывать каждое срабатывание строкой JSON в общий для
репозиториев журнал `<runDir>/history.jsonl` (время, источник, действие, репозиторий, код выхода, длительность,
версия); сбой записи журнала SHALL NOT менять результат проверки.

#### Scenario: Два push

- **WHEN** первый push проходит, второй отменён хуком, третий — с `--no-verify`
- **THEN** в журнале две строки `hook`/`pre-push`: с кодом 0 и с ненулевым кодом

#### Scenario: Журнал недоступен

- **WHEN** запись в журнал не удалась (каталог недоступен, файл занят)
- **THEN** код выхода хука тот же, что без журнала

#### Scenario: Большой журнал

- **WHEN** журнал больше 5 МБ
- **THEN** он переименовывается в `history.1.jsonl`, запись идёт в новый

### Requirement: Задание CI на PR

ОТК SHALL поставляться с шаблоном workflow Forgejo Actions, который на событие PR запускает
`gate` на Windows-раннере с платформой 1С и публикует JUnit и сводку как артефакты.

#### Scenario: PR с ошибкой запроса

- **WHEN** в PR опечатка в поле запроса
- **THEN** проверка PR красная, а в артефактах есть сводка с местом ошибки

### Requirement: Проверка всех модулей Конфигуратором в CI (designer-check)

ОТК SHALL поставляться с отдельным заданием проверки всех модулей Конфигуратором (`otk designer-check`) со всеми
ключами режимов и `-ExtendedModulesCheck`, которому предшествует отрицательный контроль; запуск —
по метке PR или по расписанию. Вердикт — по ошибкам, которых нет в базовой линии (файл принятых
ошибок в репозитории проекта).

Отрицательный контроль SHALL выполняться в своей ИБ контроля (вариант А): файловая ИБ в кэше
пользователя, одна на версию платформы, с заведомой ошибкой в серверном общем модуле конфигурации и в модуле её
расширения; `/CheckModules -Server` без `-Extension` и с ним обязан показать обе. ИБ контроля не создаётся или
контроль в ней не сработал — запасной вариант Б: заведомая ошибка грузится в серверный общий модуль копии, проверка
всех модулей обязана её показать (в результат она не попадает), затем модуль восстанавливается; загрузку не пускает
поддержка — копия снимается с поддержки (`/ManageCfgSupport -disableSupport -force`). Явные режимы
(`[designer-check] modes`) SHALL проверяться: неизвестный ключ или ни одного ключа режима — ошибка настройки
(Конфигуратор пропускает неизвестный ключ молча, а без режима отвечает «ошибок нет»). rc≠0 без разобранных ошибок —
код 2.

#### Scenario: Отрицательный контроль не сработал

- **WHEN** заведомая ошибка не найдена ни в ИБ контроля, ни внутри проверки всех модулей
- **THEN** задание падает с сообщением «проверка Конфигуратором не работает», а не считается зелёным

#### Scenario: ИБ контроля недоступна

- **WHEN** файловая ИБ контроля не создаётся (например, нет лицензии на запуск Конфигуратора для неё)
- **THEN** контроль выполняется внутри проверки всех модулей (вариант Б), сводка называет вариант и причину

#### Scenario: Опечатка в режимах

- **WHEN** в `[designer-check] modes` указан неизвестный ключ (`-Sever`) или только `-ExtendedModulesCheck`
- **THEN** задание завершается кодом 2 с ошибкой настройки, Конфигуратор не запускается

Та же проверка SHALL запускаться в прогоне gate (`gate --designer`) после проб в той же копии ИБ,
с тем же отрицательным контролем и базовой линией: её новые ошибки — находки шага `designer` единой сводки (одна
ошибка в той же строке того же файла, что находка другой проверки, — источник этой находки), один JUnit, Problems и
код выхода; сбой контроля или неразобранный вывод при rc≠0 — код 2. Выполненная целиком проверка снимает из
«не покрыто этим прогоном» и «не проверено» пункты `needs: designer:<контекст>` в своих режимах (`designer:*` —
всегда). Рабочая база пользователя (`environment.connection`) для неё не используется.

#### Scenario: gate --designer — одна сводка

- **WHEN** правка в PR даёт ошибку, которую находят и проба, и проверка всех модулей, а модуль внешнего
  соединения стоял в «не покрыто» с `needs: designer:ExternalConnection`
- **THEN** в сводке одна находка с источниками пробы и Конфигуратора, модуля нет в «не покрыто», код выхода 1;
  отрицательный контроль не сработал — код 2

#### Scenario: Ошибки типовой конфигурации

- **WHEN** полная проверка находит ошибки, уже принятые в базовой линии репозитория (типовая конфигурация
  без доработок полную проверку без ошибок не проходит)
- **THEN** задание зелёное, а сводка показывает число принятых и исправленных ошибок; новая ошибка
  делает задание красным
