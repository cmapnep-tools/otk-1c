# change-detection Specification

## Purpose
Откуда берутся изменения, которые проверяет ОТК (git, каталоги выгрузки без git, конфигурация поставщика ИБ), и
план проверки из них: изменённые модули и методы, контексты компиляции, тексты запросов, зависимые модули.

## Requirements

### Requirement: Доработки относительно конфигурации поставщика ИБ

По явному ключу `--vendor` с ИБ (`--ib` или `--connection`) ОТК SHALL проверять доработки основной
конфигурации этой ИБ относительно её конфигурации поставщика: «стало» — выгрузка основной конфигурации ИБ,
«было» — та же выгрузка с текстами модулей поставщика, восстановленными по
полному отчёту `/CompareCfg`. Состояние поддержки SHALL определяться по заголовку `Ext/ParentConfigurations.bin`
выгрузки корня ИБ, а не по файлам репозитория. Без `--vendor` поведение не меняется.

#### Scenario: Изменения разрешены

- **WHEN** заголовок `{6,0,1,…}`, в ИБ изменены два модуля поставщика и добавлен один объект
- **THEN** в плане — только изменённые строки двух модулей и все модули нового объекта; загрузки в ИБ нет;
  сводка — «доработки относительно <Name> <Version> (конфигурация поставщика ИБ)» и время `/CompareCfg`

#### Scenario: Текст поставщика восстановлен точно

- **WHEN** модуль поставщика восстановлен по основной редакции и кускам отчёта
- **THEN** он совпадает с текстом конфигурации поставщика байт-в-байт для кусков всех видов (изменено, только у
  поставщика, только в основной, замена одной строки несколькими)

#### Scenario: Табуляция неотличима

- **WHEN** в модуле из отчёта есть символ «·» (так отчёт выводит табуляцию)
- **THEN** модуль проверяется целиком, в сводке — предупреждение

#### Scenario: На поддержке без изменений

- **WHEN** заголовок `{6,1,1,…}`
- **THEN** доработок нет: `/CompareCfg` и полная выгрузка не запускаются, сводка — «конфигурация на поддержке без
  изменений», код выхода 0

#### Scenario: Снята с поддержки

- **WHEN** заголовок `{6,0,0,0,1,0}`
- **THEN** ОТК завершается с кодом 2: конфигурации поставщика в ИБ нет; подсказка — `--base-dir` с выгрузкой
  поставщика или git

#### Scenario: Повторный прогон

- **WHEN** `gate --vendor` запускается по той же ИБ второй раз
- **THEN** выгрузка «стало» обновляется инкрементально из кэша, а не полностью

#### Scenario: Файл поддержки в выгрузке не в счёт

- **WHEN** ИБ собрана из выгрузки, в `ParentConfigurations.bin` которой «на поддержке», а сама ИБ выгружает
  `{6,0,0,0,1,0}`
- **THEN** решение принимается по выгрузке ИБ: отказ с кодом 2

### Requirement: Сбор изменённых модулей

ОТК SHALL по `git diff <base>..HEAD` определять изменённые, добавленные, удалённые и
переименованные модули BSL в выгрузке Конфигуратора и записывать их в `otk.json`.

#### Scenario: Изменён общий модуль

- **WHEN** в ветке изменён `src/cf/CommonModules/X/Ext/Module.bsl`
- **THEN** `otk.json` содержит модуль с `kind = CommonModule`, `owner = ОбщийМодуль.X`, `reason = changed`

#### Scenario: Изменился только XML объекта

- **WHEN** изменён только `src/cf/Documents/Y.xml`
- **THEN** модули объекта Y в пробы не попадают, а изменение передаётся шагам `ib-build` и `static-checks` (обработчики)

#### Scenario: Нет изменений в src/cf

- **WHEN** diff не затрагивает `src/cf`
- **THEN** ОТК завершается с кодом 0 и сводкой «нечего проверять», не собирая базу

### Requirement: Изменённые методы

ОТК SHALL сопоставлять изменённые строки с методами модуля и для каждого метода сохранять
имя, признак `Экспорт`, диапазон строк и признак изменения сигнатуры.

#### Scenario: Изменена сигнатура экспортного метода

- **WHEN** у экспортной функции добавлен обязательный параметр
- **THEN** у метода `signatureChanged = true`, и шаг поиска зависимых модулей обязан его обработать

#### Scenario: Изменение вне методов

- **WHEN** изменены строки в области объявления переменных или в теле модуля
- **THEN** изменение относится к псевдометоду `<тело модуля>`, а модуль всё равно идёт в пробы

### Requirement: Контексты компиляции

ОТК SHALL определять контексты компиляции модуля по флагам XML (`Server`, `ServerCall`,
`ClientManagedApplication`, `ClientOrdinaryApplication`, `ExternalConnection`, `Global`,
`Privileged`) для общих модулей и по виду модуля и свойствам конфигурации для остальных.

#### Scenario: Общий модуль сервер + внешнее соединение

- **WHEN** у модуля установлены флаги `Server` и `ExternalConnection`
- **THEN** `contexts = ["Server", "ExternalConnection"]`

#### Scenario: Контекст недоступен локально

- **WHEN** контекст `ExternalConnection` нужен, но COM-коннектор не зарегистрирован
- **THEN** модуль получает запись в `uncovered` с причиной и `needs`, а сводка показывает её в разделе «не покрыто этим прогоном»

#### Scenario: Изменения в ветке препроцессора

- **WHEN** изменённые строки лежат внутри `#Если ВнешнееСоединение Тогда`
- **THEN** в `preprocessorContexts` есть `ExternalConnection`, и модуль пробуется в этом контексте, либо получает `uncovered`

### Requirement: Извлечение текстов запросов

ОТК SHALL извлекать из изменённых методов тексты запросов: строковые литералы, содержащие
`ВЫБРАТЬ` или `SELECT`, с продолжениями `|` и конкатенацией литералов.

#### Scenario: Литерал целиком

- **WHEN** текст запроса задан одним литералом с продолжениями `|`
- **THEN** в `queries` есть запись с полным текстом и `complete = true`

#### Scenario: Текст собран с переменной

- **WHEN** текст получен конкатенацией литерала и переменной
- **THEN** запись имеет `complete = false` и не разбирается, а сводка показывает её как «не проверен»

### Requirement: Зависимые модули

ОТК SHALL добавлять в план неизменённые модули, которые вызывают изменённый по сигнатуре,
удалённый или переименованный экспортный метод либо ссылаются на удалённый или переименованный объект метаданных.

#### Scenario: Удалён экспортный метод

- **WHEN** из общего модуля удалена экспортная процедура, которую вызывают три других модуля
- **THEN** эти три модуля добавлены с `reason = dependent` и проходят пробы и статическую сверку

### Requirement: Словари вариантов встроенного языка

ОТК SHALL брать всё, что зависит от варианта встроенного языка (ключевые слова и директивы,
имена коллекций метаданных и методов платформы, слова запросов), из подключаемого словаря, а вариант
определять по `ScriptVariant` в `Configuration.xml`. Поставляются русский и английский словари.
Ключевые слова и встроенные имена (`Справочники`/`Catalogs`, `ПолучитьФорму`/`GetForm`, `ЗНАЧЕНИЕ`/`VALUE`)
платформа принимает в любом варианте, поэтому разбор и статика SHALL понимать оба языка сразу. Имена владельцев
модулей в плане (`ОбщийМодуль.X`) и код проб SHALL быть каноническими (русскими) при любом варианте: расширение
ОТК русское и исполняется в конфигурации любого варианта.

#### Scenario: Конфигурация на английском варианте языка

- **WHEN** `ScriptVariant = English`, код модулей на английском (и местами на русском)
- **THEN** сбор изменений, статика (ссылки на метаданные, формы, предопределённые, методы платформы), разбор
  запросов, пробы COM и YAxUnit и расширенная проверка работают так же, как в русской конфигурации

#### Scenario: Неизвестный вариант языка

- **WHEN** `ScriptVariant` — вариант без словаря
- **THEN** ОТК завершается с кодом 2 и сообщением «вариант языка … не поддерживается», а не выдаёт ложных находок

### Requirement: Детерминированный план

ОТК SHALL для одной и той же пары ревизий формировать один и тот же `otk.json`
(порядок модулей, идентификаторы запросов).

#### Scenario: Повторный сбор

- **WHEN** `otk collect` запускается дважды без изменений
- **THEN** файлы побайтно совпадают

### Requirement: Готовность дерева редакции

Дерево редакции (`trees/<начало sha>`) SHALL считаться содержащим источник только по маркеру готовности
`<дерево>-<хеш src>.done`, у которого имя посчитано от его же содержимого (путь источника), а содержимое
непустое. Маркер с пустым содержимым, с именем не от своего содержимого или с повреждённой кодировкой SHALL
считаться отсутствующим: источник извлекается заново и маркер перезаписывается. Маркер, недоступный для чтения
по правам, SHALL оставаться сбоем окружения с путём к маркеру: молчаливая перезагрузка дерева скрыла бы проблему
с каталогом прогонов. Маркер объемлющего источника покрывает вложенный (расширение сценариев внутри источника
плана), если согласован сам. Снятие маркеров при извлечении (пересекающиеся источники) SHALL сравнивать
содержимое так же, как оно записано, без нормализации пробелов: иначе маркер объемлющего источника уцелеет при
сбое извлечения вложенного и следующий вызов примет неполное дерево за готовое.

#### Scenario: Исправный маркер

- **WHEN** дерево извлечено целиком, рядом лежит маркер с путём источника в содержимом и его же хешем в имени
- **THEN** повторный вызов `materialize` для этого источника и вложенных возвращает дерево без извлечения

#### Scenario: Пустой маркер

- **WHEN** рядом с деревом лежит пустой файл `<дерево>-<хеш src>.done`, а файла источника в дереве нет
- **THEN** дерево извлекается заново, файл источника появляется, маркер перезаписан

#### Scenario: Чужое имя

- **WHEN** маркер содержит путь источника, покрывающий проверяемый, но имя посчитано от другого пути
- **THEN** маркер не принимается, дерево извлекается заново

#### Scenario: Повреждённая кодировка

- **WHEN** содержимое маркера оборвано посреди символа UTF-8
- **THEN** маркер считается отсутствующим: дерево извлекается заново, маркер перезаписан

#### Scenario: Маркер без прав на чтение

- **WHEN** маркер существует, но не читается (нет прав)
- **THEN** ОТК завершается сбоем окружения с путём к маркеру, дерево не переизвлекается и не удаляется

#### Scenario: Пересечение источника с пробелом в пути

- **WHEN** извлечение `src/A /ext` сорвалось, а рядом лежит маркер источника `src/A ` (пробел — часть имени
  каталога на Linux)
- **THEN** маркер `src/A ` снят: следующий вызов извлечёт источник заново, а не примет неполное дерево
